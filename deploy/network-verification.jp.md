# VPN/プロキシのブロック：接続測定

BrainVaultは、VPNやプロキシを経由していると思われるサインインをブロックできます。同じブラウザ接続の遅延時間（RTT）を2つの方法で測定し、比較する仕組みです。このドキュメントでは、設定方法と、検出できること・できないことを説明します。

## 概要

- **リバースプロキシ（HTTPSの入口）が必要です。** そのプロキシがブラウザ接続のTCP_INFOを渡せる必要があります。直接HTTPSモードでは提供できません（[詳細](#直接httpsモード)）。
- **コンテナに追加するものはありません。** ICMP、ping、raw socket、`NET_RAW`、`NET_ADMIN`、privilegedモードは不要です。測定用の外部リクエストは送らず、外部サービス（地理的な基準サーバー、WebRTCによるアドレス検出、VPN評価リスト）も使いません。
- **デフォルトでは無効です。** プロキシを正しく設定した後にだけ、TCP測定値の信頼を有効にします。
- **完璧なVPN検出器ではありません。** この方法では検出できないVPNが多くあります（[詳細](#検出できることとできないこと)）。

基本のHTTPS設定がまだの場合は、先に[HTTPSデプロイガイド](README.jp.md)を完了してください。

## 仕組み

```text
ブラウザ -- HTTPS/WSS --> Synology DSMリバースプロキシ -- HTTP/WS --> BrainVaultコンテナ
           ① ここでTCP RTTを測定                       ② WebSocket RTTは経路全体を測定
```

1. **TCP RTT**：プロキシが、ブラウザ→プロキシ間の接続についてカーネルが測定した遅延を読み取り、リクエストヘッダーでBrainVaultへ渡します。
2. **WebSocket RTT**：BrainVaultがブラウザまでの往復時間全体を測定します。
3. **比較**：WebSocketの遅延がTCPの遅延より一貫して大きく上回る場合、間にVPNやプロキシサーバーなどの中継地点がある可能性が高くなります。

> [!IMPORTANT]
> TCP測定は、WebSocketアップグレードが通るその接続、つまり**ブラウザ→プロキシ**間の接続で行う必要があります。プロキシ→コンテナ間の接続を測定すると内部区間だけが反映され、誤検出が起きます。

NASやDockerのアドレスがプライベートIPでも問題ありません。重要なのは、BrainVaultがブラウザの公開アドレスと、入口の有効なTCP情報を受け取ることです。

## Synology DSMでの設定

### ステップ1. リバースプロキシのルールを準備

DSMの**コントロールパネル > ログインポータル > 詳細設定 > リバースプロキシ**でBrainVaultのルールを編集します（ルールがない場合は[HTTPSデプロイガイド](README.jp.md#synology-dsmリバースプロキシ)を参照）。

- ソース：HTTPS。宛先：コンテナの内部HTTPアドレス。
- **カスタムヘッダー**で**作成 > WebSocket**を選択します。
- `Origin`ヘッダーを保持し、信頼された転送経路を通じて`X-Forwarded-Proto: https`と実際のクライアントアドレスを渡します。

これらのオプションはSynologyの[DSMリバースプロキシガイド](https://kb.synology.com/en-in/DSM/help/DSM/AdminCenter/system_login_portal_advanced)でも説明されています。

### ステップ2. TCP測定ヘッダーを追加

HTTPSの入口に次の**リクエストヘッダー**を追加します。クライアントが送った値は必ず**上書き**してください。

| ヘッダー | NGINXの値 | 意味 |
| --- | --- | --- |
| `X-BrainVault-TCP-Peer-IP` | `$remote_addr` | クライアントのTCP接続の相手側アドレス |
| `X-BrainVault-TCP-RTT-Us` | `$tcpinfo_rtt` | カーネルが測定したTCP RTT、マイクロ秒単位 |
| `X-BrainVault-TCP-RTTVar-Us` | `$tcpinfo_rttvar` | カーネルが測定したTCP RTTの変動値、マイクロ秒単位 |

これらの変数はNGINXの[TCP_INFO対応](https://nginx.org/en/docs/http/ngx_http_core_module.html#var_tcpinfo_rtt)で提供されます（単位は[NGINXのソース](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_variables.c)を参照）。

> [!WARNING]
> 対応状況はDSMのバージョンやビルドによって異なります。カスタムヘッダーの画面があっても、これらの変数が存在すること、実際の値で埋められることは**保証されません**。
>
> - 生成されたプロキシ設定で変数が評価され、WebSocketアップグレード要求でBrainVaultが**数値**を受け取ることを確認してください。
> - 文字列のままの`$tcpinfo_rtt`、空の値、RTT `0`は拒否されます。
> - 固定のRTT値を手入力しないでください。
> - DSMのビルドがTCP_INFOを提供できない場合は、ブラウザの接続を直接受ける別の入口が必要です。DSMの**後段**にNGINXを追加しても元の接続は見えないため、効果はありません。

このリポジトリがNAS自体の設定を変更することはありません。

### ステップ3. BrainVaultを設定

3つのヘッダーが正しく生成され、上書きされることを確認した後、次のように設定します。`TRUST_PROXY_ADDRESSES`には、コンテナから実際に見えるプロキシのアドレスを指定してください。

```env
HTTPS_MODE=proxy
PUBLIC_ORIGIN="https://notes.example.com"
TRUST_PROXY_ADDRESSES="172.18.0.1"
TRUST_PROXY_HOPS=0
TRUST_PROXY_ALLOW_PRIVATE_CLIENTS=false
VPN_TRUST_PROXY_TCP_INFO=true
VPN_PROXY_RTT_MARGIN_MS=10
VPN_MIN_EXCESS_RTT_MS=50
```

チェックリスト：

- [ ] `TRUST_PROXY_ADDRESSES`をできるだけ狭く指定した。
- [ ] コンテナのHTTPポートを外部に公開していない。
- [ ] 上書きルールを設定した**後にだけ**`VPN_TRUST_PROXY_TCP_INFO=true`にした。（通常のプロキシは攻撃者が送ったヘッダーをそのまま転送するため、デフォルトは`false`です。）
- [ ] `/api/network-verification/probe`と`/api/collaboration/`の両方でWebSocketアップグレードが転送される。

### ステップ4. アプリで確認

1. **外部ネットワーク**（例：モバイルデータ通信のスマートフォン）から接続します。ローカルネットワークからのアクセスは意図的に例外扱いされるため、公開経路の設定が正しいことの証明になりません。
2. アカウントのセキュリティ設定で**接続を再測定**を押します。
3. 設定が正常なら、**信頼された入口で測定したクライアントTCP RTT**と、測定したWebSocket/TCP RTTが表示されます。

問題がある場合は、TCP情報の利用が無効なのか、TCP RTTがないのか、クライアント情報が一致しないのかが画面に表示されます。[トラブルシューティング](#トラブルシューティング)を参照してください。

測定値と判定のしきい値が認証前のAPIで公開されることはありません。

## その他の入口構成

- **NGINX**：同等の設定が[nginx.conf.example](nginx.conf.example)にあります。
- **`real_ip`を使うNGINX**：`real_ip`が`$remote_addr`を書き換える場合は、`X-BrainVault-TCP-Peer-IP`に`$realip_remote_addr`を使い、元のTCP接続相手を保持してください。このアドレスは検証済みのクライアントIPと一致する必要があります。
- **前段にCDNやTCPを終端する別のプロキシがある場合**：入口はブラウザではなくCDNとの接続を測定することになります。CDNのクライアントIPヘッダーを転送しても解決せず、一致しない測定情報は拒否されます。

## トラブルシューティング

| 画面の表示 | 考えられる原因 | 対処 |
| --- | --- | --- |
| TCP情報の利用が無効 | `VPN_TRUST_PROXY_TCP_INFO`が`false` | ステップ2を終えてから`true`に設定 |
| TCP RTTがない | 入口が数値のTCP_INFOヘッダーを送っていない（文字列の`$tcpinfo_rtt`、空、`0`） | 生成されたプロキシ設定を確認。TCP_INFO対応の入口を使う |
| クライアント情報が一致しない | `X-BrainVault-TCP-Peer-IP`が検証済みのクライアントIPと異なる（`real_ip`、前段のCDN） | `$realip_remote_addr`を使う、またはTCPを終端する余分な区間をなくす |
| TCPの根拠がまったくない | 重複・不正なヘッダー、信頼されていないプロキシアドレス、HTTPS以外の転送、無効な転送経路 | `TRUST_PROXY_ADDRESSES`を確認し、ヘッダーが追加ではなく上書きされているか確認 |
| LANでは動くが外部では失敗 | ローカルネットワークは例外のため、公開経路が実際には試されていない | 外部ネットワークから試す |
| 保護されたリクエストが約20秒止まる | ブラウザの測定が失敗した | 上記の測定設定を見直す |

## 設定項目

| 設定 | デフォルト | 意味 |
| --- | --- | --- |
| `VPN_TRUST_PROXY_TCP_INFO` | `false` | 明示的に信頼したローカルHTTPS入口が上書きしたTCP_INFOヘッダーを使用 |
| `VPN_MIN_EXCESS_RTT_MS` | `50` | 繰り返し観測される必要がある最小の追加遅延。ミリ秒単位（信頼度の百分率ではない） |
| `VPN_PROXY_RTT_MARGIN_MS` | `10` | ローカルリバースプロキシ区間の追加の許容誤差 |
| `VPN_ALLOW_PRIVATE_NETWORK` | `true` | 直接のLANアクセスを維持。プロキシ経由で来るプライベートクライアントには`TRUST_PROXY_ALLOW_PRIVATE_CLIENTS=true`も必要 |
| `VPN_POLICY_FAIL_CLOSED` | `true` | ブロックを有効にしたアカウントで測定の根拠がない場合にアクセスを拒否 |

**測定に失敗するとどうなりますか？**

- 測定の失敗はトンネルの検出とは**異なります**。
- `VPN_POLICY_FAIL_CLOSED=true`の場合、ブロックを有効にしたアカウントは根拠がないときもアクセスを拒否されます。`false`の場合、測定の失敗は許可しますが、検出されたトンネルは引き続きブロックします。
- ブロックを無効にしたアカウントは常にアクセスできます。
- 現在の接続をすぐにブロックしてしまうポリシーは有効にできません。
- 既存のパスワード/MFA再認証とセッション失効の保護はそのまま適用されます。過去のブロック記録と、別機能の国別ログイン制限も引き続き参照できます。

## 判定の方法

| 結果 | 意味 |
| --- | --- |
| `CLEAR` | TCP/WebSocket間に追加の遅延が観測されなかった。VPNがないことの**証明ではありません**。 |
| `TUNNEL` | 一貫した追加の遅延が観測された。VPN/プロキシとみなします。 |
| `INCONCLUSIVE` | 遅延が不安定で判断できない（WebSocketの遅延が不安定、TCPの変動が大きい、推定値が整合しない）。 |
| `UNKNOWN` | TCPの根拠がない。完了したWebSocketサンプルは保持します。 |

<details>
<summary>測定の詳細</summary>

1. ブラウザが同一オリジンの使い捨てチケットを要求し、`/api/network-verification/probe`に接続します。
2. サーバーがそのアップグレード要求のTCP_INFOメタデータを記録します。
3. サーバーが予測不能なWebSocketのpingフレームを12回送り、一致するpongフレームの往復時間を単調時計で測ります。これらはTCP上のWebSocket制御フレームで、ICMPパケットではありません。
4. ブラウザは内容を解釈できない完了トークンだけを提出します。クライアントが申告するRTTや判定は無視されます。
5. 12個のサンプルは6個ずつ連続する2つの区間に分けられます。**両方の区間**がTCP RTT + `VPN_MIN_EXCESS_RTT_MS` + `VPN_PROXY_RTT_MARGIN_MS` + TCP RTT変動値の3倍を超えた場合にだけ`TUNNEL`です。RTTが高いだけでは検出しません。1つのTCPスナップショットを複数の独立した測定として扱うことはありません。

**結果の保存方法**

- 完了トークンは、`HttpOnly`、`SameSite=Strict`属性を持つ不透明なCookieと交換されます（HTTPSでは`Secure`と`__Host-`プレフィックスも使用）。
- 結果はそのブラウザと、正確に正規化されたクライアントIPに結び付けられ、5分後に期限切れになり、ページが表示されている間は更新されます。
- 同じNATの背後にある別のブラウザ同士で結果を共有することはありません。
- パスワードログイン、MFA、パスキー、認証済みリクエスト、共同編集の再検証に適用されます。

</details>

## 制限事項

### リソースの制限

| 項目 | 制限 |
| --- | --- |
| アクティブな測定ソケット | 全体で32個、送信元IPごとに4個 |
| チケット | 送信元IPごとに毎分30枚 |
| 測定時間 | 12秒 |
| WebSocketサンプル | 12個 |
| 内部状態 | サイズ制限と有効期限のあるマップ |

チケットを含むサブプロトコル、完了トークン、Cookieはログに残さないでください。測定が失敗すると、次の保護されたリクエストが約20秒遅れることがあります。

### 検出できることとできないこと

- **検出できる**：TCP接続は中継地点で分割され、WebSocketストリームはブラウザまで続くため、安定した追加の遅延が生じる場合。
- **確実には検出できない**：
  - すべての住宅用IPのVPN。
  - TCP接続をエンドツーエンドでそのまま転送するWireGuard、OpenVPNなどのトンネル。この場合、TCP RTTとWebSocket RTTが一緒に増えます。
  - サーバーのすぐ近くにある中継サーバー、またはWebSocket制御フレームに自ら応答する中継サーバー。
- ネットワーク負荷と入口側の処理スケジュールは、両方の測定値に影響します。
- 実際に運用する前に、区別されたトラフィック（直接接続、モバイル、混雑回線、ローカルプロキシ、住宅用IPのVPN）で調整し、誤検出率と根拠を取得できる割合を別々に測定してください。検出精度の百分率は保証しません。

### 直接HTTPSモード

Node.jsが直接HTTPSを提供するモード（`HTTPS_MODE=posh-acme`）はWebSocket RTTを測定しますが、組み込みのTCP_INFO収集機能はありません。この場合は`DIRECT_TCP_INFO_UNAVAILABLE`と表示され、リクエストヘッダーでカーネルのソケットデータを代用することはできません。TCPの収集機能は、上記のDSM/NGINXを入口とする構成を対象としています。
