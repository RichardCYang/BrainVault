# HTTPS deployment

BrainVault can terminate TLS itself with Posh-ACME PEM files or continue to listen on private HTTP behind a trusted reverse proxy.

## Direct HTTPS with Posh-ACME

Posh-ACME writes `fullchain.cer` (certificate plus issuing chain) and `cert.key` (private key) in each certificate order folder. Display the exact paths for the active order in PowerShell:

```powershell
Get-PACertificate | Format-List Subject,FullChainFile,KeyFile,NotAfter
```

Configure BrainVault with either the order folder or the reported `FullChainFile` path:

```env
NODE_ENV=production
HOST="0.0.0.0"
PORT=443

PUBLIC_ORIGIN="https://notes.example.com"
WEBAUTHN_RP_ID="notes.example.com"
WEBAUTHN_ORIGIN="https://notes.example.com"
CORS_ORIGIN="https://notes.example.com"

HTTPS_MODE=posh-acme
POSH_ACME_CERT_PATH="C:/Users/service-account/AppData/Local/Posh-ACME/acme-v02.api.letsencrypt.org/example-order/fullchain.cer"
# Optional. By default BrainVault reads cert.key beside fullchain.cer.
# POSH_ACME_KEY_PATH="D:/certificates/notes.example.com/cert.key"
```

Forward slashes avoid backslash escaping surprises in Windows `.env` files. The account running BrainVault must have read permission for both files. At startup BrainVault verifies that the certificate is currently valid, covers the `PUBLIC_ORIGIN` hostname, and matches the private key; startup fails closed when a TLS file is missing or invalid.

`HTTPS_MODE=posh-acme` opens only an HTTPS listener on `HOST` and `PORT`; it does not also open port 80. Use a firewall, router, or separate HTTP redirect service when an HTTP-to-HTTPS redirect is required. BrainVault reads the files during startup, so restart the BrainVault process after a successful Posh-ACME renewal. A renewal task can use the returned certificate object as the restart trigger:

```powershell
Set-PAOrder notes.example.com
if (Submit-Renewal) {
    Restart-Service -Name BrainVault
}
```

After startup, the log should show `Posh-ACME HTTPS mode enabled`. Verify the API and WebSocket-capable browser origin:

```bash
curl -I https://notes.example.com/health
curl -I https://notes.example.com/
```

## HTTPS through a reverse proxy

Caddy, Synology Reverse Proxy, NGINX, or Nginx Proxy Manager can terminate public TLS while BrainVault remains on private HTTP. The application trusts `X-Forwarded-Proto` only when the connecting proxy matches the configured trust rule.

### BrainVault environment

A same-host proxy should normally keep BrainVault bound to loopback:

```env
NODE_ENV=production
HOST="127.0.0.1"
PORT=4000

PUBLIC_ORIGIN="https://notes.example.com"
WEBAUTHN_RP_ID="notes.example.com"
WEBAUTHN_ORIGIN="https://notes.example.com"
CORS_ORIGIN="https://notes.example.com"

HTTPS_MODE=proxy
HTTPS_REDIRECT=true
HTTPS_HEALTHCHECK_BYPASS=true
TRUST_PROXY_ADDRESSES="loopback"
TRUST_PROXY_HOPS=0
```

For a proxy in another container or host, replace `loopback` with the exact proxy IP or the narrowest practical CIDR and bind `HOST` only to the private interface reachable by that proxy. BrainVault intentionally refuses numeric hop trust because a shorter path to the backend can otherwise let a client supply forwarding headers. Catch-all `/0` CIDRs are also rejected. `TRUST_PROXY_HOPS` is retained only as a compatibility variable and must remain `0`.

`HTTPS_MODE=proxy` requires at least one `TRUST_PROXY_ADDRESSES` rule. Requests recognized as HTTPS continue normally. Plain HTTP requests are redirected with status 308 to `PUBLIC_ORIGIN`; set `HTTPS_REDIRECT=false` to return `426 HTTPS_REQUIRED` instead. `/health` remains available on the private HTTP listener by default for local checks.

### Caddy

Copy `Caddyfile.example`, change the domain/backend, and reload Caddy. A basic `reverse_proxy` forwards the original protocol and supports WebSocket upgrades automatically.

### NGINX

Copy the `map` and server blocks from `nginx.conf.example`, update the certificate paths, test with `nginx -t`, then reload. The WebSocket `Upgrade` and `Connection` headers are needed for `/api/collaboration/`.

### Nginx Proxy Manager

Create a Proxy Host with:

- Domain: `notes.example.com`
- Scheme: `http`
- Forward host/IP: the BrainVault private address
- Forward port: `4000`
- Websockets Support: enabled
- SSL certificate: selected
- Force SSL: enabled

Nginx Proxy Manager normally supplies the forwarded host/protocol headers. Do not expose port 4000 publicly; allow only the proxy network.

### Synology DSM Reverse Proxy

In **Control Panel → Login Portal → Advanced → Reverse Proxy**, create:

- Source protocol: `HTTPS`
- Source hostname: `notes.example.com`
- Source port: `443`
- Destination protocol: `HTTP`
- Destination hostname: `127.0.0.1` or the BrainVault private address
- Destination port: `4000`

Under **Custom Header**, choose **Create → WebSocket** so collaboration upgrades are forwarded. Also add `X-Forwarded-Proto` with value `$scheme` when it is not already generated by your DSM version; BrainVault intentionally requires the trusted proxy to report `https`. Attach the certificate for `notes.example.com` in DSM and optionally add a separate HTTP source rule that redirects to HTTPS. Keep the BrainVault destination port private.

### Reverse-proxy verification

After startup, the server log should show `HTTPS reverse-proxy mode enabled`. Verify:

```bash
curl -I http://127.0.0.1:4000/health
curl -I -H 'Host: notes.example.com' http://127.0.0.1:4000/
curl -I -H 'X-Forwarded-Proto: https' http://127.0.0.1:4000/
curl -I https://notes.example.com/
```

The private health check should return 200. A private non-health HTTP request should return 308 (unless redirecting is disabled), the trusted forwarded-HTTPS simulation should return 200, and the public URL should return the application without a redirect loop. Open two browser windows on the same shared page to confirm WebSocket collaboration.
