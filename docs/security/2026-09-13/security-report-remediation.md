# Security report remediation (2026-09-13)

The supplied REPORT.md was re-checked against this source archive. The changes below address the confirmed runtime risks from that report; this is not a certification that the application is vulnerability-free.

| Finding | Verification and disposition |
| --- | --- |
| BV-02-R | Confirmed and fixed. Registration now applies the per-IP limiter and schema validation before the global limiter, preventing one source from consuming the shared registration budget with requests that its own limiter or validation rejects. |
| BV-08 | Confirmed and fixed. Migration `077_custom_icon_tenant_identity.sql` changes the custom-icon primary key to `(user_id, id)`, restore no longer treats another tenant's identical icon ID as a conflict, and library restore retains an ownership-safe upsert. |
| BV-09 | Confirmed and fixed. Existing MFA factors must now approve sensitive authenticator/password changes through a short-lived, session- and auth-version-bound step-up token. Password rotation invalidates all enrolled passkeys and TOTP credentials so attacker-enrolled authenticators cannot survive incident-response password rotation. |
| BV-10 | Confirmed and fixed. TOTP source-IP blocking is enforced only at TOTP code verification. It no longer denies authenticated HTTP/WebSocket traffic, direct passkey sign-in, or passkey MFA fallback, and reaching the TOTP threshold no longer deletes unrelated pending MFA sessions. |
| BV-11 | Confirmed and fixed. Attachment filenames are NFC-normalized, stripped of NTFS alternate-data-stream suffixes and trailing filesystem-equivalent dots/spaces before extension policy is applied. |
| BV-12 | Confirmed and fixed. Restored custom-icon filenames reject Windows reserved device basenames before any filesystem path is created. |
| BV-13 | Confirmed and fixed. ACCORDION custom-icon ownership validation and rebinding now apply to legacy backup versions as well as current backups, and page-version history rebinding covers block-created, block-deleted, and block metadata updates. |
| BV-14 | Confirmed and fixed. Attachment quota accounting ignores the restore-generation marker and ignores unexpected non-file entries instead of turning them into a persistent account-wide upload failure. |
| BV-15 | Advisory versions were confirmed, but no production exploit was established in the shipped configuration: Express uses its simple query parser and URL-encoded parsing is non-extended, while the Vitest issue is development-only. Dependency versions were therefore left unchanged in this source-only remediation; upgrade `qs` to 6.16.0+ and Vitest/@vitest/mocker to a patched line when dependency compatibility is validated. |
| BV-16 | Confirmed. Stale source-level assertions affected by the fixes were updated. Verification claims below now distinguish checks actually run in this packaging environment from checks that require dependency installation or external services. |
| BV-17 | Confirmed and fixed. Final direct/collection access revocation no longer rolls back because attacker-influenced Yjs content cannot materialize. Pending history is copied into the existing bounded owner recovery vault before the collaboration lineage is retired; if bounded replay or recovery capacity is unavailable, access revocation still commits and the inert history is retained instead of keeping the collaborator authorized. Starting a new share refuses to discard any retained history that cannot first be quarantined. |
| BV-18 | Confirmed and fixed. TOTP-IP, VPN/proxy/Tor, and country-login policy mutations now accept and consume the same single-use MFA step-up token used by password changes. The browser obtains step-up proof before each policy PUT, and policy rotation clears outstanding step-up sessions after the authentication version changes. |
| BV-19 | Confirmed and fixed. Restore invalidation is workspace-scoped rather than actor-scoped. Migration `078_block_move_receipt_workspace_scope.sql` records the workspace owner on new block-move receipts and backfills resolvable legacy rows; delegated receipts for other owners are retained during a collaborator's own restore. |
| BV-20 | Confirmed and fixed. Backup database timestamps and the ISO-Z export timestamp are now format- and calendar-validated, including valid month/day ranges and leap years, before any restore insertion can reach a `DATETIME` column. Zero/invalid dates are rejected by schema validation. |
| BV-21 | Confirmed as a low-severity defense-in-depth gap and fixed. Fallback bookmark previews are structurally marked `verified: false`; server and browser normalization force unverified image/favicon fields to empty strings, so a policy-blocked fetch cannot later acquire trusted preview-media semantics. Arbitrary HTTP(S) bookmark links remain supported. |

### Applying the update

Run the normal dependency installation and database migration workflow (`npm ci`, `npm run db:migrate`, `npm run build`) before restarting the application. Migration `076_mfa_step_up_sessions.sql` creates short-lived MFA step-up state, migration `077_custom_icon_tenant_identity.sql` changes custom-icon identity from a global key to a tenant-scoped composite key, and migration `078_block_move_receipt_workspace_scope.sql` scopes block-move replay receipts to the workspace they protect. Automatic database bootstrap applies pending migrations when enabled; otherwise apply migrations explicitly before starting this version.

API clients that add, rename, replace, or remove MFA factors, change the account password, or modify the TOTP-IP/VPN/country login-defense policies must include a valid `stepUpToken` when the account already has an enrolled factor. The browser obtains that token by confirming an existing TOTP code or passkey. A successful password change intentionally removes existing TOTP/passkey credentials so they must be enrolled again. Existing attachment download defenses remain in place. The archive retains the original project paths and Git metadata and adds no audit-log or report-log files.

### Validation and limits

- Focused dependency-free Node regression tests for BV-17 through BV-21 and adjacent account-security/block-move controls passed in the packaging environment.
- Browser JavaScript syntax for the modified `public/app.js` was checked directly with Node.
- The packaging environment could not resolve `registry.npmjs.org`, and its preinstalled Node 22.16.0 is below BrainVault's declared patched runtime floor. Therefore a clean `npm ci`, full project type-check/build, Vitest suites, and the complete `npm run verify:security` workflow were not claimed as executed here. The project engine guard and lockfile were not weakened or changed.
- No live MariaDB migration/transaction test, browser WebAuthn ceremony, deployed reverse proxy, or multi-instance environment was exercised. Run the normal full CI and migration suite in a supported Node environment before production deployment.

Reference guidance: [OWASP Multifactor Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html) recommends requiring an existing enrolled factor before changing MFA factors. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) recommends reauthentication for sensitive account changes.
