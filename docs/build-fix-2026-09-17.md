# BrainVault 빌드 오류 수정 보고서

작성일: 2026-09-17 (Asia/Seoul)  
대상: 제공된 `BrainVault.zip`, `brainvault@1.0.0`  
수정 범위: 기존 소스 3개 파일에서 1줄 추가·6줄 삭제, 회귀 테스트 및 본 보고서 추가

## 1. 결론과 검증 범위

제보된 19개 오류는 서로 독립적인 19개 결함이 아니라 두 가지 원인에서 발생한다.

1. 구조화 메타데이터 검증기에 복제된 북마크 제한값에서 `previewTokenLength`가 누락되어 TS2339 1개가 발생한다.
2. `username: string`을 받는 서비스 함수 `clearPasswordLoginAccountLimit`가 6개 Express 라우트에 미들웨어로 잘못 등록되어 뒤쪽 콜백의 문맥적 타입 추론이 깨지고, `req`, `res`, `next`에 대해 TS7006 18개가 발생한다. 이 함수는 실제 요청 객체로 호출하면 런타임 오류도 일으킨다.

두 원인에 대한 소스 수정을 적용했다. 새 회귀 테스트 30개 및 기존 관련 테스트 29개가 통과했다. 원본/수정본에서 실제 선언과 라우트 등록을 추출한 **축소 타입 재현**에서는 오류가 TS2339 1개+TS7006 18개에서 0개로 바뀌었다.

**전체 프로젝트의 `npm run build` 성공은 이 검증 환경에서 확인하지 못했다.** 환경의 Node 버전이 프로젝트 요구보다 낮고, npm 레지스트리 DNS 접근 실패로 의존성 설치와 Mermaid 다운로드를 완료하지 못했다. 축소 타입 재현 및 독립 테스트를 전체 프로젝트 빌드 성공으로 해석하면 안 된다. 자세한 구분은 5절에 있다.

## 2. 원인 A: 북마크 제한값 불일치

### 2.1 원본 상태

`src/lib/bookmark.ts`의 북마크 정규화 코드에는 이미 다음 제한값이 존재한다.

```ts
previewTokenLength: 64,
```

반면 `src/lib/structured-metadata-integrity.ts`의 로컬 `bookmarkLimits`에는 이 속성이 없는데, 같은 파일의 검증 코드는 다음과 같이 참조하고 있었다.

```ts
const previewToken = optionalString(
  item.previewToken,
  `${path}.previewToken`,
  bookmarkLimits.previewTokenLength
);
```

따라서 상수 객체의 추론된 타입에 해당 속성이 없다는 TS2339가 발생한다. 단순히 TypeScript 버전을 바꿔서 해결할 문제가 아니라 실제 선언과 사용의 불일치다.

### 2.2 수정

무결성 검증기의 `bookmarkLimits`에 정규화 코드와 동일한 `previewTokenLength: 64`를 추가했다. 환경 설정과 다른 의존성이 있는 북마크 모듈 전체를 검증기로 새로 가져오거나 모듈 구조를 재편하지 않고, 이번 결함에 필요한 최소 변경만 적용했다. 추가한 회귀 테스트는 두 모듈의 저장 메타데이터 관련 제한값 전체가 일치하는지 비교한다. 네트워크 수집 전용 `htmlBytes`, `redirects`는 비교 대상에서 제외한다.

**64는 입력 길이 상한이고, 유효한 비어 있지 않은 토큰 형식은 기존대로 43자 base64url이다.** 아래 정규식은 변경하지 않았다.

```ts
/^[A-Za-z0-9_-]{43}$/
```

따라서 64자리 토큰까지 유효하게 인정하도록 규칙을 완화한 것이 아니다. 부재·null·빈 문자열에 대한 기존 처리도 유지했다. 이 형식 검사는 암호학적 서명 검증 자체가 아니며, 기존 정규화 코드의 HMAC 검증 로직도 수정하지 않았다.

## 3. 원인 B: 문자열 처리 함수의 잘못된 미들웨어 등록

### 3.1 문제가 된 함수의 실제 계약

`src/middleware/auth-rate-limit.ts`의 원본 함수는 다음과 같다.

```ts
export async function clearPasswordLoginAccountLimit(username: string): Promise<void> {
  const normalized = username.trim().toLowerCase();
  if (normalized) {
    await loginAccountRateLimit.resetKey(hashRateLimitKey("account", normalized));
  }
}
```

위 코드는 계정 이름을 정규화하고 해당 계정의 실패 제한 키를 초기화하는 보조 함수다. Express의 `(req, res, next)` 미들웨어가 아니다. 원본 주석 역시 별도로 인증된 복구 작업 이후에만 호출하고, 공유 IP 제한은 초기화하지 말라고 명시한다.

그러나 이 함수 이름이 라우트의 미들웨어 인수 목록에 직접 들어 있었다.

```ts
authRouter.put(
  "/totp-ip-block-policy",
  requireAuth,
  accountReauthenticationRateLimit,
  clearPasswordLoginAccountLimit, // 원본의 잘못된 등록
  loginLockoutRecoveryRateLimit,
  validate({ body: totpIpBlockPolicySchema }),
  async (req, res, next) => {
    // 기존 비즈니스 처리
  }
);
```

### 3.2 왜 함수 등록 위치가 아니라 콜백 매개변수에 오류가 나타나는가

TypeScript는 함수가 사용되는 위치의 타입을 통해 매개변수를 추론한다. 공개된 Express 타입 정의는 일반 `RequestHandler`를 받는 라우트 오버로드와, 오류 처리 함수까지 허용하는 더 넓은 `RequestHandlerParams` 오버로드를 제공한다. 오류 처리 함수의 첫 번째 인수는 `err: any`다.

문자열을 받는 함수는 일반 요청 핸들러와 맞지 않지만, 더 넓은 오류 처리 함수 타입과 TypeScript의 함수 매개변수 호환성 규칙이 결합되면 등록 지점에서 직접 거부되지 않을 수 있다. 대신 마지막 콜백의 문맥적 타입이 모호해져 `req`, `res`, `next`가 암묵적 `any`로 남는다. `strict` 설정에서 이를 거부하므로 6개 콜백 × 3개 매개변수 = 18개 TS7006이 나온다.

이 설명은 실제 라우트 등록과 상수 선언을 추출한 축소 타입 모델에서도 19개 오류를 같은 코드별 개수로 재현하고, 잘못된 등록 제거 및 제한값 추가 후 0개가 되는 것으로 확인했다. 다만 이 모델은 전체 Express 선언 패키지와 전체 프로젝트를 컴파일한 것이 아니며, 확인에 사용한 TypeScript도 전역 5.8.3이다. 프로젝트 잠금 버전 5.9.3을 사용한 전체 빌드와 구별해야 한다. 조사한 공개 타입 소스는 조회 시점의 upstream master다.

### 3.3 타입 표기만 추가하면 남는 실제 결함

다음과 같이 마지막 콜백에 타입을 강제로 붙이는 것만으로는 잘못 등록된 함수가 제거되지 않는다.

```ts
async (req: Request, res: Response, next: NextFunction) => { /* ... */ }
```

Express는 일반 미들웨어 호출 시 첫 번째 인수로 요청 객체를 전달한다. 그러면 위 보조 함수는 문자열 대신 요청 객체에 대해 `.trim()`을 실행한다. 실제 원본 함수 선언을 추출해 요청 형태 객체를 전달한 독립 실행에서 다음 오류를 확인했다.

```text
TypeError: username.trim is not a function
```

따라서 `any` 추가, `strict` 해제, `@ts-ignore`, 타입 단언 또는 콜백 타입 표기만으로 오류를 숨기는 수정은 하지 않았다.

### 3.4 수정한 라우트

아래 경로는 각 라우터 내부의 상대 경로다. 잘못 등록된 `clearPasswordLoginAccountLimit,` 한 줄씩만 삭제했다.

| 파일 | 메서드 | 경로 |
| --- | --- | --- |
| `src/routes/auth.routes.ts` | PUT | `/totp-ip-block-policy` |
| 동일 | DELETE | `/totp-ip-blocks/:ipAddress` |
| 동일 | PUT | `/vpn-block-policy` |
| 동일 | PUT | `/country-login-policy` |
| 동일 | POST | `/password` |
| `src/routes/passkey-login.routes.ts` | POST | `/options` |

인증, 재인증 요청 제한, 잠금 복구 요청 제한, 입력 검증, 패스키 IP 요청 제한, 동일 출처 검사, JSON 요청 검사와 원래 순서는 유지했다. 계정 제한 초기화 함수 자체도 수정하지 않았다.

### 3.5 유지한 정상 호출

다음 두 정상 호출과 필요한 import는 그대로 유지했다.

```ts
// auth.routes.ts: 인증된 로그인 잠금 복구 처리
await clearPasswordLoginAccountLimit(username);

// passkey-login.routes.ts: 성공한 패스키 로그인 검증 처리
await clearPasswordLoginAccountLimit(result.user.username);
```

따라서 이 수정은 계정 잠금 복구 기능을 제거하는 것이 아니라, 인증 절차와 관계없이 보조 함수가 미들웨어처럼 실행되던 잘못된 등록을 제거하는 것이다.

### 5.3 완료하지 못한 검증

**`npm ci`:** 현재 Node v22.16.0이 프로젝트 요구를 충족하지 못해 EBADENGINE으로 중단되었다. 진단용으로 명령행에서만 engine 검사를 일시 해제하고 설치 스크립트 없이 재시도했으나, 네트워크 제한으로 설치를 완료하지 못했다. `.npmrc`, 잠금 파일, 프로젝트 엔진 요구는 변경하지 않았다. 이 과정의 부분 설치물은 배포 ZIP에 포함하지 않았다.

**`npm run build`:** 실제 명령을 실행했지만 `vendor:mermaid`에서 아래 오류로 중단되어 `tsc` 단계에 도달하지 못했다.

```text
TypeError: fetch failed
[cause]: Error: getaddrinfo EAI_AGAIN registry.npmjs.org
```

이는 이 검증 환경의 DNS/다운로드 문제다. 사용자가 제공한 로그에서는 Mermaid 11.17.2의 무결성 검증과 다운로드가 성공했으므로, 원래의 19개 TypeScript 오류를 Mermaid 문제로 진단한 것은 아니다. 정상 동작하던 vendoring 절차는 수정하지 않았다.

**`npm run verify:data-loss`:** 검증 스크립트를 실행했으나 필요한 `tsx`가 설치되지 않아 실패했다. 성공으로 집계하지 않았다.

전체 `npm test`/Vitest, 전체 `npm run check`, 실제 MariaDB 연결 및 브라우저·WebAuthn 하드웨어·HTTP 통합 동작의 성공은 확인하지 못했다. 위 독립 테스트 결과를 이들 통합 검증 결과로 확대 해석하면 안 된다.

## 6. `.git` 및 원본 ZIP 보존

작업 및 테스트용 디렉터리에는 `.git`을 추출하지 않았다. Git 명령으로 상태를 갱신하거나 커밋·리셋하지 않았다. 최종 ZIP은 원본 ZIP의 항목을 기반으로 구성하고, 변경되지 않은 파일의 로컬 ZIP 레코드를 그대로 복사했다.

최종 패키징 검증은 다음 조건을 모두 요구한다.

- 원본의 `.git` 44개 항목(일반 파일 28개, 디렉터리 16개)이 모두 유지된다.
- `.git` 파일별 SHA-256과 모든 항목의 로컬 ZIP 레코드가 원본과 바이트 단위로 일치한다.
- `.git`의 ZIP 중앙 디렉터리 레코드까지 원본과 바이트 단위로 일치한다. 따라서 ZIP이 기록하는 시각·권한·속성·추가 필드·주석도 유지된다.
- 원본 971개 ZIP 항목은 삭제되지 않고, 소스 3개 이외의 원본 파일 내용은 모두 동일하다.
- 회귀 테스트와 본 보고서 2개만 추가하여 최종 ZIP은 973개 항목을 갖는다.
- 부분 설치된 `node_modules`, 검증용 임시 파일, 생성된 `dist`는 추가하지 않는다.
- 원본 업로드 ZIP 자체의 SHA-256도 작업 전후 동일하다.

파일 시스템에 압축을 푸는 도구가 설정하는 접근 시각 등 ZIP 형식에 원래 기록되지 않은 속성까지 보증하는 의미는 아니다. 보존 대상은 제공된 원본 ZIP의 실제 내용과 메타데이터다. 최종 해시와 검증 결과는 별도 검증 기록에 수록한다.

## 7. 사용자 환경에서 실행할 명령

프로젝트가 이미 요구하는 Node 범위를 만족하고 npm 레지스트리에 접근 가능한 환경에서 실행한다. 지원 범위를 낮추거나 `engine-strict`를 끄지 않는다.

```sh
node --version
npm --version
npm ci
npm run build
node --test tests/build-regressions.node.test.mjs
npm test
```

`npm ci`에는 빌드용 TypeScript 등 개발 의존성도 필요하다. 배포 셸이 개발 의존성을 생략하도록 설정되어 있다면 설치 단계에 `npm ci --include=dev`를 사용한다. `npm ci`는 기존 `node_modules`를 다시 설치하되 `package.json`이나 잠금 파일을 갱신하는 설치 명령이 아니다.

원본과 동일하게 ZIP 루트에 프로젝트 파일 및 `.git`이 들어 있다. 기존 운영 폴더에 합칠 때는 사용자별 `.env`와 데이터·업로드 파일을 별도로 보호해야 한다. 이 수정에는 데이터베이스 초기화, 마이그레이션, 저장 데이터 삭제 작업이 포함되지 않는다.

## 8. 조사한 공식·1차 자료

프로젝트 결함과 수정 위치는 제공된 소스 자체를 근거로 판단했다. 아래 자료는 TypeScript의 문맥적 추론, Express 미들웨어 계약, 제한 키 초기화 API와 설치 명령의 의미를 확인하는 데 사용했다. 조회일은 2026-09-17이다.

1. TypeScript — `noImplicitAny`: 추론 불가능한 매개변수가 암묵적 any가 될 때의 오류.
2. TypeScript — Type Inference: Contextual Typing.
3. Express — Using middleware: 요청·응답·next 인수와 제어 전달 계약.
4. DefinitelyTyped — express-serve-static-core 타입 정의: RequestHandler, ErrorRequestHandler, RequestHandlerParams 및 라우트 오버로드. 조회 시점 upstream master이며 잠금 버전 전체의 현장 설치 검증을 대신하지 않는다.
5. express-rate-limit — Instance API: `resetKey`의 명시적인 키 초기화 동작.
6. npm v10 — `npm ci`: 잠금 파일 기반의 정리 설치와 개발 의존성 포함 옵션.
