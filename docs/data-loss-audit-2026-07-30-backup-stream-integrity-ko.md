# BrainVault 백업 스트림 무결성 감사 (2026-07-30)

## 결론

첨부파일 백업 ZIP을 생성할 때, 사전 검사 이후 스테이징 파일의 내용이 **동일한 크기로 변경**되면 기존 구현은 변경을 감지하지 못한 채 ZIP 중앙 디렉터리까지 완성할 수 있었습니다. 생성된 ZIP의 헤더와 `brainvault.json`에는 이전 CRC32/SHA-256이 기록되지만 실제 페이로드는 변경된 바이트이므로, 이후 복원 과정의 무결성 검사에서 거부됩니다.

원본 워크스페이스를 즉시 삭제하는 결함은 아닙니다. 일반 애플리케이션 경로는 스테이징 파일을 다시 쓰지 않으므로 발생 가능성은 제한적이지만, 로컬 파일 변조·스토리지 오류·향후 코드 경로의 우발적 재사용이 발생하면 다운로드 성공을 신뢰한 뒤에야 백업이 사용할 수 없음이 드러날 수 있습니다. 따라서 **영향도 높음, 발생 가능성 낮음, 종합 중요도 중간(Medium)**의 백업 무결성 위험으로 분류했습니다.

## 재현 조건

1. `prepareUserDataBackup()`이 첨부파일을 스테이징하고 크기·CRC32·SHA-256을 계산합니다.
2. 검사 완료 후 ZIP 스트리밍 전 또는 스트리밍 중 스테이징 파일 바이트가 바뀝니다.
3. 파일 크기는 기존과 동일하게 유지됩니다.
4. 기존 `ZipWriter.add()`는 바이트 수만 비교하고 사전 계산 CRC32를 ZIP 헤더에 그대로 기록합니다.
5. 내보내기는 완료되지만 복원 시 CRC32 또는 SHA-256 불일치로 거부됩니다.

재현 명령:

```bash
npm run reproduce:backup-stream-integrity-loss
```

## 수정

- `ZipWriter.add()`가 실제로 출력하는 모든 청크에 대해 CRC32를 다시 계산합니다.
- 첨부파일은 매니페스트에 기록된 SHA-256도 스트리밍 중 다시 계산합니다.
- 크기, CRC32 또는 SHA-256 중 하나라도 사전 검사값과 다르면 중앙 디렉터리를 완성하지 않고 실패합니다.
- `writeUserDataBackup()`이 첨부파일의 사전 검사 SHA-256을 `ZipWriter`에 전달하도록 연결했습니다.
- 버퍼 엔트리도 호출자가 넘긴 CRC32를 신뢰하지 않고 실측값과 대조합니다.

## 회귀 검증

- 동일 크기 스테이징 파일 변경을 감지하는 Node 의존성 비필요 테스트
- 정상 바이트의 ZIP 완성 테스트
- 잘못된 버퍼 CRC32 거부 테스트
- 종합 `verify:data-loss`에 소스 가드와 취약/수정 상태 재현을 통합
- 현재 수정된 `HEAD`에서도 과거 취약 커밋을 Git 이력에서 찾아 실행하도록 협업 부트스트랩 재현 스크립트를 교정

## 운영 의미

수정 후에도 스트리밍이 시작된 뒤 오류가 발생할 수 있으므로 HTTP 응답은 중간에 종료될 수 있습니다. 이는 완성됐지만 복원 불가능한 ZIP을 정상 다운로드로 제공하는 것보다 안전한 fail-closed 동작입니다. 사용자는 실패한 다운로드를 다시 시도할 수 있고, 서버는 원본 워크스페이스나 첨부파일을 변경하지 않습니다.
