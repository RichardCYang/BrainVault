# 3단계 설계: 페이지 크기 제한 없애기

상태: 3-B·3-C·3-D·3-E 구현, 3-A 보류 (아래 "최종 구현 현황") · 작성일: 2026-11-14

## 최종 구현 현황 (2026-11-14, 2차)

모두 실제 MariaDB와 헤드리스 Edge로 측정했다(최상위 블록 N개, 짧은 문단).

| | 개인 페이지 10,000 | 개인 페이지 20,000 | 공유 페이지 5,000 |
|---|---|---|---|
| 열기 (응답 + 그리기) | 1.5 s | 2.4 s | 0.6 s |
| Enter로 나누기 (제자리 확인) | — | 4.7–5.5 s | 3.2 s |
| 수정 전 | 그리기만 4.7 s | 순서 요청이 413으로 실패 | — |

- **3-C 순서 변경 압축 전송 (`src/lib/block-order-request.ts`):**
  - 형제 블록 전체 목록을 블록마다 객체로 보내던 것을, id 문자열 하나와 버전 문자열 하나로 보낸다.
  - 서버는 이를 원래 형식으로 풀어 **같은 검증과 같은 멱등성 해시**를 거친다. 따라서 복구용 임시 저장(recovery draft)과 재전송은 바꿀 필요가 없었다.
  - 행별 UPDATE는 500행 단위 일괄 UPDATE로 바꿨다. 행마다 기대 버전, 페이지 범위, 안전 정수 상한 조건은 그대로 두었고, 한 행이라도 안 바뀌면 전체를 되돌린다.
  - 처음 설계한 "블록 하나만 바꾸는 위치 지정 이동"은 하지 않았다. 형제 순서를 다시 매기는 비용이 서버 시간의 대부분이라, 위치 지정으로 바꿔도 이 비용은 그대로 남는다.
- **3-B 화면 근처만 그리기:**
  - 블록 300개가 넘는 페이지는 화면에서 두 화면 넘게 떨어진 행에 `content-visibility: auto`를 적용한다. 레이아웃과 그리기를 건너뛰고, 텍스트 칸 높이 맞추기도 행이 가까워질 때 한다.
  - 화면 근처 행과 편집 중인 행에는 적용하지 않는다. 메뉴나 핸들이 잘리지 않게 하려는 것이다.
  - DOM은 모든 행을 만든다(완전한 가상화는 아님). 그래서 "페이지 전체가 메모리에 있다"고 가정하는 기존 코드 13곳은 그대로 맞다.
- **Enter와 삽입 속도:**
  - 서버가 확인한 삽입이면 큰 페이지에서는 새 행 하나만 끼워 넣는다(`insertConfirmedBlockRowInPlace`). 작은 페이지는 기존처럼 전체를 다시 그린다.
  - 서버 응답 반영도 블록마다 트리를 처음부터 찾던 방식(제곱 비용)에서 한 번 훑는 방식(`updateBlocksInState`)으로 바꿨다.
  - 블록 20,000개 페이지에서 Enter: 12.3 s → 4.7 s.
- **개인 페이지 한도 20,000 블록.** 바이트 예산(원본 16MB, 응답 32MB)은 그대로다.
- **3-D 공유 페이지 한도 5,000 블록 (`sharedPageResourceLimits`):**
  - 공유 페이지는 Yjs 문서 하나에 들어가는데, 서버는 구조체(struct)가 100,000개를 넘는 문서 업데이트를 거부한다. 이 보안 상한은 유지한다.
  - 일반 블록 하나가 구조체 10개를 쓰고 편집할수록 늘어서, 5,000개면 예산의 절반이 남는다.
  - 공유가 시작되는 세 경로(페이지 공유, 컬렉션 공유, 공유 컬렉션으로 이동)와 실시간 편집 세션에서 먼저 거절한다. 브라우저는 재연결을 반복하지 않고 안내만 띄운다.
  - 수정 전에는 블록 20,000개 페이지를 공유하면 열 수 없었고, 브라우저가 재연결을 반복하다 429 오류를 받았다.

**보류: 3-A 나눠 읽기.** 최대 크기(블록 20,000개)에서도 페이지 응답 6.8MB를 1.1–1.5초에 받고, 열기 전체가 2.4초다. 나눠 읽으면 첫 화면이 1–2초 빨라진다. 대신 일부 블록만 받은 상태에서 편집이 시작될 수 있는데, 이 코드베이스의 데이터 손실 방지 장치(복구 기록, 저장 대기, 형제 전체 목록 확인)는 모두 "페이지 전체를 받은 상태"를 전제로 한다. 얻는 시간에 비해 위험이 크다고 보고 하지 않았다. 페이지 한도를 20,000보다 올려야 할 때 다시 검토한다.

## 구현 현황 (2026-11-14, 1차)

설계를 구현하기 전에 실제 DB와 헤드리스 Edge로 큰 페이지를 측정했다. 그 결과 순서가 바뀌었다. 측정 결과 먼저 고쳐야 할 문제가 두 가지 있었다.

| 측정 (최상위 블록 N개) | 600 | 2,000 | 5,000 | 10,000 |
|---|---|---|---|---|
| 페이지 응답 | 25 ms | 79 ms | 0.2 s | 0.4 s |
| 화면 그리기 (수정 전) | 1.0 s | **8.0 s** | — | — |
| 화면 그리기 (수정 후) | 0.5 s | 1.0 s | 2.4 s | 4.7 s |
| Enter로 블록 나누기 | 0.4 s | 0.5 s | 1.5 s | 실패 (아래 2번) |

1. **화면 그리기가 블록 수의 제곱으로 느려지던 문제 → 수정함.** 텍스트 칸마다 높이를 맞추면서 매번 페이지 전체 레이아웃을 다시 계산했다(`fitTextareaHeight`가 전체 시간의 94%). 높이 맞추기를 한 프레임에 모아 레이아웃을 한 번만 계산하게 바꿨다(`fitTextareaHeights`, `scheduleTextareaFit`).
2. **최상위 블록이 500개를 넘는 페이지에서 순서가 깨지던 버그 → 수정함.** 중간에 블록을 만들면 서버는 일단 맨 끝에 붙이고, 형제 블록 전체 순서를 보내서 제자리로 옮긴다. 그런데 이 요청이 500개까지만 허용돼서, 새 블록이 페이지 맨 아래로 갔다. 상한을 페이지 블록 한도와 같게 맞췄다.
3. **페이지 블록 한도 2,000 → 5,000.** 형제 블록 전체 순서를 보내는 방식은 공통 요청 검사(`REQUEST_VALIDATION_MAX_NODES = 50,000`)에 걸려 약 9,999개가 한계다. 5,000개는 측정상 무리가 없고, 순서 변경 요청도 검사 범위 안이다. 테스트로 보장한다: `tests/page-block-limit.node.test.mjs`.
4. **3-E 일부 구현.**
   - 긴 붙여넣기가 페이지 한도를 넘으면 "새 하위 페이지에 붙여넣기"를 제안한다.
   - 페이지 한도 오류 7종을 7개 언어로 번역했다. 이전에는 서버의 영어 메시지가 그대로 보였다.

**남은 것 (이 문서의 원래 설계):**

- **3-C 위치 지정 이동:** 블록 하나만 바꾸는 순서 변경이다. 5,000개를 넘기려면 꼭 필요하다. 순서 변경은 복구용 임시 저장(recovery draft)과 재전송까지 엮여 있어서, 그 구조를 함께 바꿔야 한다.
- **3-A 나눠 읽기, 3-B 화면 근처만 그리기:** 10,000개에서 그리기가 4.7초 걸린다.
- **3-D 공유 페이지.**

## 1. 목표와 원칙

페이지 하나에 걸린 제한을 사용자가 느끼지 못하게 만든다. 지금 걸려 있는 제한은 다음과 같다.

- 블록 2,000개
- 텍스트(markdown) 4MB
- 메타데이터 8MB
- 렌더링 결과(HTML) 8MB
- 원본 데이터 합계 16MB
- 응답 하나 32MB

원칙은 1·2단계와 같다.

- **없애는 것:** "페이지 전체"에 걸린 제한
- **남기는 것:** "요청 한 번", "블록 한 개", "동시 처리 수"에 걸린 제한. 사용자가 느끼지 못하는 한도라 남겨 둔다.
- **기존 데이터:** 그대로 동작해야 한다. 스키마는 컬럼과 인덱스를 추가하는 방식으로만 바꾼다. 기존 값을 다시 쓰는 마이그레이션은 하지 않는다.

## 2. 지금 제한이 있는 이유 (코드 기준)

| 위치 | 페이지 전체를 한 번에 다루는 부분 | 결과 |
|---|---|---|
| `GET /api/pages/:pageId` (`src/routes/page.routes.ts`) | 권한 확인과 모든 블록을 트랜잭션 하나에서 읽고, 응답 하나로 반환 | 응답 32MB, 원본 16MB 예산(`src/lib/page-resource-limits.ts`) |
| `assertStoredPageResourceBudget` | 쓰기 때마다 페이지 전체 블록의 길이를 다시 셈 (`LIMIT maxBlocks + 1`) | 블록 2,000개 제한 |
| 클라이언트 `state.selectedPage.blocks` (`public/app.js`) | 블록 트리 전체를 메모리에 두고 `renderSelectedPage()`가 전부 그림. `flattenBlocks()` 호출 13곳 | 큰 페이지에서 브라우저가 느려짐 |
| 블록 순서 변경 `persistBlockOrder(parent, orderedIds)` | 같은 부모 아래 형제 블록 전체의 id 목록을 보냄 | 형제 블록 수만큼 요청이 커짐 |
| 실시간 협업 Yjs 문서 (`collaboration-materialization.ts`, `document.getMap("blocks")`) | 페이지 하나 = Y.Doc 하나 | 방 하나의 메모리가 페이지 크기에 비례(`COLLABORATION_ROOM_MEMORY_MAX_BYTES`) |
| 버전 기록 (`page-version-history.ts`) | 변경분만 저장하고 바이트 상한이 있음 | **문제 없음.** 페이지 크기와 무관 |

DB 인덱스 `idx_blocks_page_sort(page_id, sort_order)`와 `idx_blocks_parent_sort(parent_block_id, sort_order)`가 이미 있어서, 블록을 순서대로 나눠 읽는 데 새 인덱스는 필요 없다.

## 3. 설계

작은 단계부터 따로 출시할 수 있게 나눈다. 단계마다 그 자체로 쓸모가 있고, 되돌릴 수 있다.

### 3-A. 나눠 읽기 (서버 읽기 경로) — 효과 큼, 위험 낮음

- **새 엔드포인트:** `GET /api/pages/:pageId/blocks?cursor=<sortOrder,id>&limit=<n>`
  - 최상위 블록을 `(sort_order, id)` 순서로 `limit`개(기본 200)씩 돌려준다. 각 블록의 하위 블록은 함께 보내되, 블록 개수와 바이트 상한으로 묶는다.
  - 응답에는 `contentVersion`과 `nextCursor`를 넣는다.
- **일관성:** 첫 요청에서 받은 `contentVersion`을 이후 요청마다 `ifContentVersion`으로 보낸다. 값이 바뀌었으면 서버가 `409 PAGE_CHANGED`를 돌려주고, 클라이언트는 처음부터 다시 읽는다. 지금의 "트랜잭션 하나로 일관된 읽기"를 낙관적 버전 확인으로 대신하는 방식이다. 페이지가 다른 계정 소유로 바뀌는 restore 세대 변화도 같은 방식으로 막는다. `users.attachment_generation`을 함께 확인한다.
- **제한 이동:** `assertPageResponseBudget`과 `assertPageRenderBudget`는 응답 한 번 단위로 그대로 쓴다. `assertStoredPageResourceBudget`의 블록 수 검사는 없앤다. 쓰기 경로는 블록 하나와 해당 부모의 형제 목록만 검사한다.
- **호환성:** 기존 `GET /api/pages/:pageId`는 남긴다. 작은 페이지(예: 블록 500개 이하)는 지금처럼 한 번에 받는다. 서버가 `blocksTruncated: true`와 커서를 주면 클라이언트가 나머지를 이어 받는다. 옛 클라이언트도 작은 페이지에서는 그대로 동작한다.

### 3-B. 화면에 보이는 부분만 그리기 (클라이언트) — 효과 큼, 위험 중간

- `state.selectedPage.blocks`는 그대로 두되, 아직 받지 않은 구간은 "자리표시자 구간"으로 표시한다.
- 렌더링은 화면 근처 구간만 하고, 나머지는 측정해 둔 높이만큼 빈 공간으로 둔다. `IntersectionObserver`가 화면 근처에 온 구간을 감지해서 3-A로 받아 온다.
- **위험 지점:** `flattenBlocks()`를 쓰는 13곳(편집 기록, 검색 강조, 저장 대기, 복구 등)이 "페이지 전체가 메모리에 있다"고 가정한다. 이 13곳을 하나씩 다음 두 종류로 나눈다.
  - 받아 온 블록만으로 충분한 곳 (대부분)
  - 페이지 전체가 필요한 곳 (예: 페이지 전체 검색, 전체 선택 후 삭제). 이런 곳은 먼저 "전체 받기"를 한 뒤 실행한다.
- **편집 중인 블록:** 화면 밖으로 나가도 DOM에서 지우지 않는다. 저장되지 않은 입력, IME 조합 중인 글자, 캐럿을 지키기 위해서다.

### 3-C. 순서 키 바꾸기 — 블록이 많을 때 필요, 위험 중간

- **문제:** 지금은 블록 하나를 옮겨도 형제 블록 전체의 순서를 다시 보낸다. 형제가 수만 개면 요청 하나가 커지고, 순서 충돌도 잦아진다.
- **해결:** `blocks.order_key VARCHAR(64) NULL` 컬럼을 추가하고, 정렬 기준을 문자열 사이 값(fractional index)으로 바꾼다.
  - 블록 하나를 옮길 때 그 블록의 `order_key`만 바꾸면 된다.
  - 앞뒤 키 사이에 새 키를 만든다. 길이가 커지면 해당 형제 구간만 다시 번호를 매긴다.
- **기존 데이터:** `sort_order`는 지우지 않는다.
  - 새 컬럼이 비어 있으면 `sort_order`로 정렬한다. `ORDER BY order_key IS NULL, order_key, sort_order, id`처럼 쓴다.
  - 키는 블록을 처음 옮기거나 새로 만들 때 그 형제 구간만 채운다. 한꺼번에 다시 쓰는 마이그레이션은 없다.
  - 백업 v7은 `sort_order`를 계속 내보내고, `order_key`는 선택 필드로 추가한다(v8). 옛 백업을 복원하면 `order_key`가 NULL인 채로 들어가고, 정렬은 `sort_order`로 똑같이 된다.

### 3-D. 실시간 협업 나누기 — 가장 어려움, 마지막에

- **문제:** 공유 페이지는 Y.Doc 하나에 페이지 전체가 들어간다. 큰 페이지 하나가 방 메모리 예산을 다 쓸 수 있다.
- **안 A (추천):** 공유 페이지에 별도 상한을 둔다. 고정값이 아니라 1·2단계처럼 `방 메모리 예산 ÷ 동시 방 수` 같은 계산식으로 정한다. 상한에 가까워지면 "이 부분을 하위 페이지로 분리"를 제안한다. 큰 문서를 여럿이 동시에 편집하는 경우는 드물고, 안 B의 위험이 크다.
- **안 B:** 최상위 블록 구간마다 하위 문서(Yjs subdocument)를 둔다. 구간 사이 블록 이동은 "삭제 + 삽입"을 lineage로 묶어 처리하고, 구간마다 따로 SQL에 반영한다. 블록 이동, 복구, 압축(compaction), 여러 서버 인스턴스 간 처리를 전부 다시 검증해야 한다. 이미 있는 `reproduce:*` 회귀 스크립트(materialization 손실, 서버 간 compaction 손실 등)를 모두 다시 통과해야 한다.

### 3-E. 한도에 닿았을 때의 UX

- 남는 한도(응답 한 번, 공유 페이지 상한)에 닿아도 413 오류로 끝내지 않는다. "선택한 제목 아래 내용을 하위 페이지로 옮기기"를 제안하고, 한 번에 실행되게 한다.
- 옮긴 자리에는 하위 페이지 링크 블록을 남긴다. 옮기기는 서버 트랜잭션 하나로 처리하고, 버전 기록에 "이동"으로 남겨서 되돌릴 수 있게 한다.

## 4. 보안·가용성 점검

| 위험 | 대책 |
|---|---|
| 큰 `limit` 요청으로 서버 메모리 소모 | `limit` 상한(최대 500)과 응답 바이트 상한(32MB). 이미 있는 `admitPageProjection` 동시 처리 제한을 그대로 사용 |
| 커서 조작으로 다른 페이지 블록 노출 | 요청마다 권한 확인. 커서는 페이지 id와 묶고 서명하거나, 서버가 다시 검증 |
| 나눠 읽는 중에 restore가 일어나 다른 세대의 데이터가 섞임 | `contentVersion`과 `attachment_generation`이 하나라도 다르면 409로 처음부터 다시 읽기 |
| 순서 키가 무한히 길어짐 | 키 길이 상한(64자). 넘으면 해당 형제 구간만 다시 번호 매기기 |
| 공유 페이지 방 메모리 | 3-D 안 A의 계산식 상한과 기존 `CollaborationMemoryBudget` |

## 5. 검증 계획

1. **실제 DB 대량 페이지:** 블록 20,000개짜리 페이지를 만들어 다음을 확인한다. 나눠 읽기 결과와 기존 한 번에 읽기 결과가 같은지, 쓰는 중에 읽어도 일관된지, 순서 변경 요청 크기가 일정한지.
2. **헤드리스 Edge:** 스크롤하며 모든 구간을 받아 오는지, 편집 중 블록이 유지되는지, IME 입력, 붙여넣기 분할(2단계)과 함께 동작하는지.
3. **호환성:** 옛 클라이언트와 새 서버, v1~v7 백업 복원, `order_key`가 NULL인 기존 데이터의 정렬이 그대로인지.
4. **회귀:** 전체 테스트와 `verify:security`, `verify:data-loss`, 그리고 3-D를 하면 `reproduce:*`의 협업 회귀 스크립트 전부.
