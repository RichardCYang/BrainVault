# コレクション共有

BrainVaultは**カスタムコレクション**に対するコレクションレベルのアクセスをサポートします。コレクション権限は、そのコレクションと、ネストされた子孫ページを含め、そのコレクションに属するすべての通常ページへ適用されます。この機能はブラウザーUI、REST API、MariaDBマイグレーション、実効アクセスresolver、Yjs共同編集サーバー、バックアップ／復元経路、耐久性テストまでエンドツーエンドで実装されています。

## UIで**コレクション共有**を見つける

コレクション共有の入口はグローバルではなく、意図的にコンテキスト依存です。

1. コレクション所有者、または`ADMIN`権限を持つ共同編集者としてサインインします。
2. 左サイドバーで**カスタムコレクションの名前**をクリックします。その中の文書ページは開かないでください。
3. コレクションのランディングビューで、**ページ追加（Add page）**の横にある**コレクション共有（Share collection）**を選択します。
4. 既存のBrainVaultログインIDを入力し、`READ`、`WRITE`、`ADMIN`から選択します。

次のいずれかに該当するとボタンは非表示になります。

- 現在のビューが仮想の**既定コレクション（Default Collection）**である
- コレクションのランディングビューではなく個別文書ページを開いている
- サインイン中アカウントが`READ`または`WRITE`権限しか持たない
- アクティブ項目が永続化されたカスタムコレクションではない

サイドバーのコレクション3点メニューは共有の入口ではありません。通常ページ1つの直接共有は、そのページの**共有（Share）**ボタンから引き続き利用できます。

## 権限モデル

| 権限 | 実効ページロール | 文書の読み取り | 共有文書の編集 | ページ／コレクション操作の管理 | 共有管理 |
| --- | --- | --- | --- | --- | --- |
| `READ` | `READER` | はい | いいえ | いいえ | いいえ |
| `WRITE` | `EDITOR` | はい | はい | いいえ | いいえ |
| `ADMIN` | `ADMIN` | はい | はい | はい、共有コレクション範囲内 | はい |

`READ`クライアントは、既に共有されている通常ページのライブYjsストリームへ参加して現在および将来の文書更新を受信できますが、WebSocketサーバーは接続を書き込み不可としてマークし、バイナリ文書書き込みを`COLLABORATION_READ_ONLY`で拒否します。

`WRITE`は通常の共有文書編集を許可しますが、共有管理やページ管理のコントロールは公開しません。

`ADMIN`は意図的により強い権限です。共有コレクション範囲内でコレクション共有および対応ページ／コレクション管理操作に必要な管理チェックを満たします。直接ページ共有の作成は所有者専用のままであるため、コレクション管理者が、自身を認可しているコレクション権限より長く残る低優先度の権限を作成することはできません。コレクション管理者はスコープ制限され、共有コレクション外へページを移動しようとすると`COLLECTION_ADMIN_SCOPE_REQUIRED`で拒否されます。

## スコープと継承

マイグレーション`068_collection_sharing.sql`は2つの構造を作成します。

- `collection_shares`: `(collection_id, user_id)`ごとに1つの権限を保持し、`READ`、`WRITE`、`ADMIN`、`shared_by`、因果的`generation`トークンを持ちます。
- `page_collection_memberships`: コレクション自身とすべての子孫ページに対するmaterializedカスタムコレクションメンバーシップです。

コレクションはルートオブジェクトであり、その下のページはネストできます。メンバーシップは再帰的なため、権限は直接の子だけでなく子孫ページまで届きます。

コレクション配下でページを作成すると、そのメンバーシップは直ちに書き込まれます。ページサブツリーを移動するとBrainVaultはそのサブツリーのメンバーシップを置き換えます。移動によって実効共有集合が変わる場合、サーバーはアクティブ書き込みをfenceし、復旧候補を保持し、影響するYjs文書generationをリセットして、置換された共同編集lineageだけを切断します。

## コレクション権限と直接ページ権限

同じメンバーページに両方のアクセスを持つユーザーでは、コレクション権限が優先されます。実効アクセスresolverは`page_shares`より先に`collection_shares`を確認します。

つまり次のようになります。

- コレクション`READ` + 直接ページ`EDIT` => コレクション権限が存在する間は実効`READER`
- コレクション`WRITE` + 直接ページ`EDIT` => コレクション権限による実効`EDITOR`
- コレクション`ADMIN` + 直接ページ`EDIT` => コレクション権限による実効`ADMIN`

ワークスペース所有者が作成した独立の直接ページ権限は、コレクション権限の下に保存されたまま残る場合があります。BrainVaultはコレクション共有がそれを上書きするとき、そのgenerationをローテーションし、遅延したソケットクリーンアップが後のセッションを追い出さないようにします。コレクション権限が削除され、所有者作成の直接権限がまだ有効なら、その直接ページ権限が再び有効になります。コレクション管理者が取り消されると、BrainVaultはメンバーページ上で`shared_by` provenanceがその取り消された管理者を示す直接ページ権限も削除します。これにより、管理者が仕込んだ権限が管理権限の取り消し後も残ることを防ぎます。

## REST API

すべてのエンドポイントには通常の認証済みBrainVaultセッションが必要です。コレクション共有は、コレクション所有者またはそのコレクションで実効ロールが`ADMIN`のアカウントが管理できます。

| メソッド | ルート | 用途 |
| --- | --- | --- |
| `GET` | `/api/collections/:collectionId/shares` | 現在のコレクション権限を一覧表示します。 |
| `POST` | `/api/collections/:collectionId/shares` | 既存アカウントを`READ`、`WRITE`、`ADMIN`で追加します。 |
| `PATCH` | `/api/collections/:collectionId/shares/:userId` | 現在の`expectedGeneration`を使って権限を変更します。 |
| `DELETE` | `/api/collections/:collectionId/shares/:userId` | 現在の`expectedGeneration`を使って権限を削除します。 |

作成本文の例:

```json
{
  "username": "collaborator-id",
  "permission": "WRITE"
}
```

更新本文の例:

```json
{
  "permission": "ADMIN",
  "expectedGeneration": "cshare_current_generation"
}
```

削除本文の例:

```json
{
  "expectedGeneration": "cshare_current_generation"
}
```

Generationは因果トークンです。別セッションが既に権限を変更している場合、古い更新／削除要求は置換後の権限を変更せず`409 COLLECTION_SHARE_GENERATION_CHANGED`で失敗します。

## リアルタイム共同編集の動作

コレクション共有は、実効的に共有される各**通常文書**に、直接ページ共有と同じ共同編集モデルを適用します。コレクション自身はYjs文書ではありません。

文書に最初の実効共同編集者が付与されると、BrainVaultは正規SQLスナップショットから新しい共同編集lineageを開始します。書き込み可能な所有者／`WRITE`／`ADMIN`ユーザーはYjs更新を送信できます。`READ`ユーザーは同期状態を受信しますが書き込めません。権限の降格または取り消し時には、古い書き込み権限を切断する前に復旧admissionを保持します。

コレクション権限を削除しても、すべてのメンバーページの共同編集を無条件に無効化するわけではありません。サーバーはまず、取り消された管理者が作成したメンバーページ直接権限を削除し、その後、所有者が独立に作成した直接権限も含め、ページごとに実効共有を再計算します。文書の最後の実効共有がなくなり、受理済みYjs更新がすべて安全にmaterializeされた場合にのみ、その文書の共同編集履歴を破棄します。

## バックアップと復元

現在のバージョン5バックアップでは`data.pageShares`とともに`data.collectionShares`が必要です。コレクションレコードはコレクションID、安定した共同編集者アカウントID、ユーザー名、権限、作成時刻、更新時刻を保持します。復元は破壊的なワークスペース置換の前に共同編集者の身元を検証し、`page_collection_memberships`を再構築し、元の権限タイムスタンプを保持したまま新しいgenerationでコレクション権限を再作成します。

明示的な`collectionShares`より前の古いバージョン4アーカイブでは、復元後も残るコレクションIDに対して現在有効なコレクション権限を暗黙に削除せず保持します。`updated_at`より前のバージョン4コレクションレコードも、履歴タイムスタンプのfallbackでインポートできます。v4より前のバックアップはコレクション共有データを宣言できず、v5が厳格な現在のエクスポート契約です。

## トラブルシューティング

### ボタンが表示されない

まず**カスタムコレクション名**をクリックし、コレクションのランディングビューを見ていることを確認してください。最も一般的なのは、コレクション内の文書を開いている、既定コレクションを使っている、所有者／`ADMIN`ではなく`READ`/`WRITE`でサインインしているケースです。

### 直接ページ編集者が読み取り専用になった

そのアカウントにコレクションレベルの`READ`権限も付いていないか確認してください。メンバーページではコレクション権限が優先されるため、コレクション権限が存在する間、`READ`は意図的に直接ページ`EDIT`を上書きします。

### 権限変更で409が返る

共有ダイアログを更新または開き直し、最新の権限generationで再試行してください。権限の変更と削除はgenerationチェックされるため、古いブラウザー操作が新しいアクセス判断を上書きできません。

### 保留中の共同編集処理によってアクセス削除がブロックされる

共同編集書き込みがまだ許可されている、または最新の受理済みYjs状態が安全にmaterializeされていない場合、BrainVaultはfail-closedで動作します。アクティブ文書の同期／materializeを完了させてから共有変更を再試行してください。
